# Direct WorldManager Semantic Standby Frontier

Status: semantic implementation is intentionally on standby as of 2026-08-08.
This document is the resume map. It records only work that remains open after
the implemented `WM-SC1` through `WM-SC11` bounded path, `WM-K1` through
`WM-K5B`, project genesis/substrate binding, and the currently proven ARO
reconstruction-to-verification path.

Current active product frontier:
[T3-Informed Alternate Direct GUI Experiment](./DIRECT_T3_ALTERNATE_GUI_EXPERIMENT.md).

## Resume Invariants

The pause changes priority, not architecture:

- Direct remains the semantic and persistence authority.
- The hierarchical worldmodel remains the only canonical semantic worldstate.
- The WorldManager control plane, epistemic ledger, semantic history, and raw
  runtime evidence remain distinct stores with typed references between them.
- Candidate, audited, authorized, admitted, and executed remain materially
  different states.
- A renderer may project or request transitions; it may not manufacture
  semantic standing, authority, evidence, or completion.
- Existing bounded `ImplementationPatch` SC11 acceptance is a completed
  foundation, not a reason to claim all artifact classes are generalized.

## Pending Frontier, In Dependency Order

### 1. `WM-K6` — general planning-to-execution continuation

Continue an admitted general plan through:

```text
ImplementationContract
  -> implementation ResolvedTaskConstitution
  -> role handoff packet
  -> worker-start transition
  -> actual Direct implementation session
  -> separately enforced tool/effect requests
  -> closure-witness evaluation
  -> project-memory candidate
  -> Project Manager admission and upward status
```

Required proof:

- a WorkThread becomes active only through worker start;
- project policies are reflected consistently in prompt, tools, approvals, and
  completion evaluation;
- completion requires evidence-bearing closure witnesses;
- a worker result cannot write project or world state directly.

The accepted SC11 `ImplementationPatch` lifecycle should be reused for typed
artifacts and assurance gates. `WM-K6` still owns the general plan execution
bridge rather than being declared complete by that narrower proof.

### 2. Authoritative project-world activation and constitutional porting

The current genesis path admits a project constitution, provisions a native
WSL or Windows workspace, proves the resident substrate, and freezes thread
environment inheritance. It still needs:

- governed promotion of a provisioned project into the authoritative
  hierarchical worldmodel;
- project focus gated by the exact graph-activation witness;
- an explicit project-port operation with custody and source-of-truth
  migration law;
- step-level multi-environment selection for tasks that lawfully require both
  Windows and WSL rather than only the project primary environment.

Porting must remain a constitutional operation over one semantic source of
truth. Copying databases and treating both substrates as authoritative is not
an acceptable implementation.

### 3. Canonical user-authored policy lifecycle

The current compiler can adapt settled rules into task policy closure. The
full user-authored policy boundary remains:

```text
policy utterance
  -> candidate PolicyObject / PolicyException
  -> scope, force, targets, inheritance, precedence, and provenance review
  -> authorized canonical admission or revision
  -> deterministic obligation closure
  -> minimal prompt projection and causal enforcement
```

This must include conflict resolution, explicit exception authority,
supersession/revision lineage, and truthful projection of configured versus
currently operative policy.

### 4. SC11 generalization and runtime hardening

The bounded end-to-end `ImplementationPatch` game is complete. Follow-on work
is deliberately narrower than “implement SC11”:

- generic manager ledger-provider lanes beyond the currently compiled worker
  and exact auditor paths;
- production delivery debounce/coalescing rather than flushing every appended
  event independently;
- a true suspended-provider resume primitive for contexts that cannot be
  handled by idle-role wake or safe-boundary deferral;
- additional artifact constitutions only when backed by an explicit lifecycle,
  assurance, admission, and recovery game.

### 5. `WM-SC12` — recursive ODEU control circuit

Implement the repo-grounded sequence from
[Recursive ODEU Control Method — Repo Analysis](./RECURSIVE_ODEU_CONTROL_METHOD_FOR_WORLDMANAGER_v0.1_REPO_ANALYSIS.md):

1. recursive kernel and trusted source-slot registry;
2. bounded frontier scheduler and semantic-context compilation;
3. directional expansion artifact lifecycle;
4. child ODEU recursion with typed exclusion instead of silent option loss;
5. upward ancestry, shared-premise discovery, and governed convergence;
6. typed join and versioned parent return;
7. integration proof around existing project genesis;
8. semantic UX and architecture-self dogfood.

The scheduler is structural, not semantic. Slot contracts decide what semantic
work is due; models author open content inside those slots; SC11 governs the
standing of resulting artifacts.

### 6. `WM-K7` — production renderer hardening

After K6 and activation truth are stable, complete:

- minimal production projection;
- per-event and background activity;
- distinct queued/running posture across multiple projects;
- object-centered semantic zoom over the same canonical event lineage;
- interrupt, retry, and recovery controls;
- narrow responsive preservation.

The alternate Direct GUI experiment may supply reusable geometry and component
mechanics. It must not be mistaken for completion of K7's semantic projection
or authority requirements.

### 7. Modality and live acceptance

- Add live voice as an ingress/egress adapter over the same typed event and
  result contracts; do not create a second voice-only semantic pipeline.
- Record a real-account live K4/planning acceptance witness. Deterministic
  provider tests remain useful but do not satisfy this promotion witness.

## Resume Gate

Before resuming semantic implementation:

1. select one bounded item above;
2. reconcile its source spec against current code and newer upstream Codex
   capabilities;
3. write the exact completion game and non-authorities;
4. preserve existing store custody and restart verification;
5. add local regression evidence before any live-provider or canonical-world
   promotion claim.

Until then, semantic code should receive only compatibility or defect fixes
needed to keep the current Direct shell operational.
